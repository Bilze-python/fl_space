# 科研 Agent 建设与幻觉治理建议（SpaceFL 专用）

> 目标：把现在的“LLM + 检索 + 规划/解读流水线”升级为**可验证、可审计、可复现**的科研智能体，
> 重点解决：参数幻觉、数字幻觉、引用幻觉、结论越界。

---

## 一、先定位：现在的系统属于哪一类 Agent

| 形态 | 特征 | 风险 |
|---|---|---|
| Prompt 链 | 固定几步调用 LLM | 不具备工具纠错能力 |
| **工作流 + LLM 节点（当前）** | 检索 → 规划 → 评审 → 解读，步骤固定 | 可控，但每一步都可能编造 |
| 有界工具循环（建议目标） | 允许 3–5 步“检索/校验/重试” | 可靠性与灵活性的平衡点 |
| 开放式自主 Agent | 自己拆任务、自己调工具、自己决定停止 | 科研场景不建议，幻觉与不可复现会放大 |

**结论：科研平台不应追求“全自主”，应建设“有界 Agentic Workflow”**：
固定主流程 + 有限工具循环 + 强制验证器；LLM 负责组织语言，不负责事实。

---

## 二、一个 Agent 由什么组成

```
用户目标
  │
  ▼
① 目标与策略层：目标、约束、权限、停止条件
  │
  ▼
② 编排器 Orchestrator：状态机 / 有界 ReAct（最多 N 步）
  │
  ├── ③ 工具层（强类型 schema）
  │      ├─ literature.search / read_page
  │      ├─ archive.list / read_metrics
  │      ├─ metrics.compute（Python，不让 LLM 算）
  │      ├─ plan.validate / experiment.run（沙箱）
  │      └─ citation.verify
  │
  ├── ④ 检索与知识层：BM25/向量、分块、页码、元数据
  │
  ├── ⑤ 记忆层：会话摘要、研究目标、实验登记、缓存
  │
  ├── ⑥ 生成层：LLM provider（DeepSeek/离线规则）
  │
  ├── ⑦ 验证层：schema、数字、引用、计划可执行性、证据覆盖率
  │
  └── ⑧ 观测与评估：trace、成本、幻觉回归集
  │
  ▼
输出：结论 + 证据 + “尚不能支持的结论” + 验证状态
```

### 最小可用 Agent 的 8 个件

1. **目标/指令**：研究目标、允许动作、禁止动作；
2. **模型**：provider 抽象、失败回退、JSON 模式、温度 0；
3. **工具**：每个工具都有输入/输出 schema、错误码、超时；
4. **编排**：确定性主流程 + 有限重试，不能无限自我循环；
5. **知识/检索**：分块、页码、来源、可引用片段；
6. **记忆**：会话状态、目标、历史实验、证据缓存；
7. **验证/护栏**：结构化校验、引用核验、权限与只读；
8. **评估/观测**：每次运行可回放，有 golden set 和指标。

## 三、Agent 常见问题（科研场景尤其致命）

| 问题 | 表现 | 治理 |
|---|---|---|
| **事实幻觉** | 编造方法、结论、作者 | 检索优先、证据覆盖率门槛、拒答 |
| **数字幻觉** | 编造准确率、增益、时延 | 数字只由 Python 计算，LLM 只引用 facts |
| **引用幻觉** | 页码/引文不存在、张冠李戴 | 引用必须带 doc_id + page + 原文 span，逐条核验 |
| **参数幻觉** | 计划说“关闭卸载”，配置却是 `max_offload_iter=1` | 计划 schema + 语义标志 + 配置 diff |
| **结论越界** | 单种子说显著、近似实现说复现 | 结论分级：实测/推断/假设；强制“不能支持”段 |
| **工具误用** | 选错工具、参数类型错、重复调用 | 强类型 schema、参数校验、调用预算 |
| **上下文超限** | 长文档塞满上下文，遗忘目标 | 分页检索、摘要 + 引用、上下文预算 |
| **不可复现** | 相同输入不同输出 | 温度 0、固定 seed、缓存、trace |
| **提示注入** | 论文/网页里藏“忽略之前指令” | 检索内容一律当数据，不作为系统指令 |
| **评估困难** | 看起来都对，无法量化 | golden set + 引用/数字/拒答指标 |
| **成本/延迟** | 多轮 LLM 调用 | 缓存、分级模型、超时、离线回退 |
| **过度自主** | 自己改目标、自己跑危险工具 | 有界步数、人类确认、只读/沙箱 |

## 四、SpaceFL 当前的典型幻觉风险（基于现有实现）

### 1. 计划文本与执行参数不一致

现有链路：`service.generate_plan()` → `planner.generate_plan()` → `analyzer.review_plan()`。
LLM 生成的计划文本可能写“关闭卸载”，但 `conditions.params.max_offload_iter` 实际是 1 或 2。
**这类问题靠 LLM 评审不可靠**——评审本身也可能误读。必须由代码做：

```text
计划语义标志（offload_enabled: true/false）
  ↔ 执行器参数（max_offload_iter / offload_every）
  ↔ 计划文本中的断言
```

三者不一致 → 直接判为不可执行/需修正。

### 2. 评审结论与结构化指标矛盾

结构化 `review.metrics.checks` 由代码生成，但 `review.content` 由 LLM 生成；
二者可能冲突（例如 checks 说“变量未变化”，参数实际变了）。
建议：**结构化 checks 为唯一事实源**，LLM 只能解释 checks，不能推翻它。

### 3. 分析报告中的数字不是从档案计算出来的

`analyze_experiment()` 应先用 Python 计算指标，再把 `facts` 交给 LLM；
如果让 LLM 从原始 history 文本“读”数字，就会出现四舍五入错误、单位错误、编造指标。
原则：**LLM 不产生数字，只排列数字**。

### 4. 引用/页码可能对不上

`library.ask` / `digest` 返回的 citations 带 `doc_id`、`page`、`quote`；
目前 quote 做过清洗，但没有逐条验证“quote 是否真的出现在该页文本中”。
需要：`quote in page_text` 的规范化子串校验；失败则丢弃引用或重检索。

### 5. 模式标签可能误导

计划/分析返回 `mode: llm | offline`；如果降级后仍用“大模型结论”措辞，会误导用户。
建议：所有结论卡片显示 `生成模式 + 证据覆盖率 + 验证状态`，而非只显示 provider 名称。

## 五、三层防线（建议直接落地）

### 第一层：输入层——先有证据，再生成

1. **检索优先**：所有结论必须先拿到 `evidence`（doc/page/span 或 archive/metric）；
2. **facts 由代码算**：准确率、差值、时延、样本守恒等一律 Python 计算；
3. **工具强类型**：每个工具返回 Pydantic/dataclass 结构，禁止返回裸文本；
4. **检索内容当数据**：论文/情报中的任何指令都不执行（防提示注入）。

### 第二层：生成层——LLM 只做“写作”

1. 计划：LLM 只输出 JSON，字段由 schema 定义；数字/枚举由代码校验；
2. 分析：LLM 收到 `facts` 与 `citations`，只写解释性文字；
3. 引用：生成时只能引用 evidence 列表里的 id，不能自由写页码；
4. 温度 0、JSON mode、超时、失败回退离线规则；
5. 约束句式：不确定就写“证据不足”，不要补全。

### 第三层：输出层——验证器 + 证据覆盖率

```python
# 建议新增 fl_space/research/verifier.py
verify_numeric_claims(text, facts, tolerance=1e-6)
verify_citations(citations, library_index)   # quote 必须能在 page_text 中找到
verify_plan(plan, executor_schema)           # 参数范围、语义标志、可执行性
verify_consistency(review_checks, review_text)  # LLM 解释不能与 checks 矛盾
evidence_coverage(claims)                    # 有证据的 claim 比例
```

输出结构建议：

```json
{
  "content": "...",
  "claims": [
    {"id": "c1", "text": "...", "type": "numeric", "value": 3.44, "unit": "%",
     "evidence": ["archive:fedleo_offload_seed42"], "verified": true}
  ],
  "citations": [
    {"doc_id": "lib_...", "page": 2, "quote": "...", "verified": true}
  ],
  "unsupported": ["单种子不能证明统计显著性"],
  "verification": {"numeric": "pass", "citation": "pass", "coverage": 0.83}
}
```

UI 上直接显示：**已验证 / 未验证 / 证据不足**；未通过验证的 claim 不应进入正式结论。

## 六、Agent 建设路线图（按投入产出排序）

### P0（1–2 周，先止血）

1. 新增 `verifier.py`：
   - 数字 claim 与 facts 对齐；
   - 引用 quote 子串校验；
   - 计划参数范围/语义标志校验；
   - review checks 与 review 文本一致性检查；
2. 计划 schema 增加 `offload_enabled` 等**语义标志**，执行前做参数 diff；
3. 分析/问答/计划接口返回 `verification` 字段；
4. UI 增加“证据/未验证”标签 + “尚不能支持的结论”固定区域；
5. 建 30 条 golden set（10 文献问答、10 计划、10 分析/拒答），加入 CI。

### P1（1–2 个月，工程化）

1. 工具注册表：`tools/` 下每个工具带 JSON schema、超时、错误码；
2. 编排器改为有界状态机（最多 5 步，允许“检索→校验→重试”）；
3. 混合检索：BM25 + 向量；分块带 page/offset；引用 span 持久化；
4. `claims ledger`：每条 claim 有证据 id，前端可点开；
5. trace/observability：每次运行记录工具调用、token、延迟、验证结果；
6. 回归指标：引用准确率、数字一致率、计划可执行率、拒答正确率、幻觉率。

### P2（长期）

1. 多轮“草稿→验证→修正”循环（有上限）；
2. 实验执行人类确认 + 沙箱；
3. 跨档案矛盾检测、文献间冲突标注；
4. 面向论文写作的“可引用结论生成器”；
5. 审计日志与权限模型。

## 七、评测：没有 golden set 就没有“幻觉治理”

### 建议的最小 golden set（50 条）

| 类型 | 数量 | 期望 |
|---|---:|---|
| 文献问答 | 15 | 答案 + 正确页码 |
| 实验计划 | 10 | 参数正确、可执行、有对照 |
| 档案解读 | 10 | 指标与档案一致 |
| 无证据问题 | 10 | 明确拒答/说证据不足 |
| 注入/陷阱问题 | 5 | 不执行文档内指令、不编造 |

### 每次回归看 6 个指标

1. **引用准确率**：citation quote 能在原文对应页找到；
2. **数字一致率**：文本数字与 facts 一致；
3. **计划可执行率**：schema + 参数 + 语义标志通过；
4. **拒答正确率**：无证据问题不硬答；
5. **结论越界率**：单种子/近似实验不被写成显著/论文复现；
6. **延迟与成本**：P50/P95、每任务 token。

目标值建议：引用准确率 ≥95%，数字一致率 100%，计划可执行率 100%，
无证据问题拒答率 ≥90%，结论越界率 ≤5%。

---

## 八、给 SpaceFL 的一句话架构建议

> **把 LLM 从“答案生成器”降级为“证据组织器”**：
> 代码负责计算与校验，检索负责事实，LLM 负责解释与表达；
> 输出的每条结论都必须带证据 id 和验证状态，不能验证的结论默认不展示。
